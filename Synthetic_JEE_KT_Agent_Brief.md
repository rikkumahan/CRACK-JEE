# Agent Brief: Synthetic JEE Learner Data + Lightweight Knowledge Tracing

## Mission

We currently have **no real student interaction dataset**.

The immediate goal is to determine, validate, and then implement a credible pipeline for:

> **Real JEE questions + controllable synthetic student agents → longitudinal student interaction data → lightweight Knowledge Tracing models (especially BKT, PFA, and LKT) → rigorous evaluation.**

This is intended as the initial research/engineering foundation for a longer-term JEE Personal Performance Engine.

## VERY IMPORTANT: Validate Before Implementing

**Do not start coding the simulator or KT pipeline immediately.**

Before implementation, independently validate all major assumptions against primary/leading research sources and available implementations.

The agent must first produce a research validation report covering:

1. Whether synthetic student interaction data is an accepted and useful methodology for Knowledge Tracing research.
2. What prior work has actually demonstrated about synthetic-vs-real KT performance.
3. What assumptions are commonly used to generate synthetic learner behavior.
4. Whether those assumptions create evaluation bias or make a KT model artificially advantaged.
5. What data fields are required by BKT, PFA, LKT, and later models such as ReKT/GKT.
6. What public JEE datasets actually contain: questions, answers, concepts, difficulty, solutions, or real student interactions.
7. Whether there are any public JEE student-interaction datasets suitable for KT, rather than only question banks.
8. Licensing / usage constraints of candidate JEE datasets.
9. Appropriate train/validation/test splitting for longitudinal student interactions and how to prevent temporal leakage.
10. Whether an independent rule-based/stochastic learner simulator is a scientifically defensible way to generate JEE trajectories.
11. Whether the proposed student-agent variables are sufficient, and which ones are unsupported or over-simplified.
12. Whether BKT/PFA/LKT can reasonably be evaluated from synthetic data with known hidden ground truth.
13. Which evaluation metrics should be used for next-response prediction and latent-state recovery.
14. Whether there are better or simpler alternatives to the proposed simulation architecture.
15. Which parts should remain deterministic and which parts genuinely benefit from an LLM.
16. What can realistically transfer from synthetic JEE interactions to future real student data.
17. Whether the entire approach is feasible on ordinary developer hardware and what, if anything, needs a remote server/GPU.

**Only after this validation should implementation begin.**

The agent must cite primary papers, official repositories/documentation, and original datasets wherever possible. Avoid relying on blog posts or search snippets when a primary source exists.

# 1. Core Research Hypothesis

Use **real JEE questions as the environment** and create a population of synthetic students whose responses are generated by explicit learning and behavioral mechanisms.

The synthetic students should not be random answer generators.

They should be controllable generative learners with hidden state.

Conceptually:

```text
REAL JEE QUESTIONS
        +
JEE concept / difficulty metadata
        +
CONTROLLED SYNTHETIC STUDENT AGENTS
        ↓
LONGITUDINAL INTERACTION DATA
        ↓
BKT / PFA / LKT
        ↓
PREDICTION + STATE-RECOVERY EVALUATION
```

The purpose is to create a controlled experimental environment before real student data becomes available.

---

# 2. What the Synthetic Student Represents

Each synthetic student should have a hidden learner state that the KT model does **not** receive directly.

Potential parameters include:

```text
Knowledge
├── concept-level mastery
├── prerequisite dependencies
└── multi-concept competence

Learning
├── learning rate
├── forgetting rate
└── practice effects

Behavior
├── guessing tendency
├── careless-error tendency
├── calculation-error tendency
├── reading/misinterpretation tendency
└── time-pressure sensitivity

Performance
├── baseline solving speed
├── confidence calibration
└── response-time variability

Intervention response
├── worked-example sensitivity
├── hint/scaffolding sensitivity
├── practice sensitivity
└── timed-practice sensitivity
```

The agent must investigate which of these are actually supported by educational measurement / KT literature rather than assuming all are necessary.

# 3. Real JEE Questions as the Environment

Use real JEE Main / JEE Advanced questions wherever licensing and availability permit.

For each question, build structured metadata such as:

```text

exam
year
shift
subject
chapter
topic / concept(s)
difficulty
question_type

```

A question may involve multiple concepts.

Represent this explicitly rather than forcing every question into one topic:

```text

```

The agent must validate whether weighted multi-skill mappings are appropriate and how existing KT literature handles multi-KC questions.

# 4. Synthetic Student Response Generation

For every question, the synthetic student should use its hidden state + question characteristics + recent history to generate a stochastic outcome.

Conceptually:

```text
hidden mastery
+ question difficulty
+ required concepts
+ prerequisite state
+ time since practice
+ learning/forgetting
+ behavioral traits
        ↓
P(correct)
        ↓
sample outcome
        ↓
time taken
        ↓
confidence
        ↓
error mechanism
```

Do **not** reduce this to:

```text
mastery > difficulty → correct
else → wrong
```

That would be too deterministic and unrealistic.

Instead, the probability of success should depend on multiple factors and contain controlled randomness.

---

# 5. Error Mechanism Simulation

A wrong answer should have a plausible cause rather than being an undifferentiated failure.

Potential mechanisms:

```text
CONCEPT_GAP
CONCEPT_APPLICATION
FORMULA_RECALL
CALCULATION
SIGN
UNIT
READING
GUESS
TIME_PRESSURE
QUESTION_SELECTION
CARELESS
```

The agent should validate this taxonomy against real educational-error literature and determine whether it should be simplified, merged, or expanded.

Possible generation mechanism:

```text
P(error_type | student_state, question_state, context)
```

The exact probability model must be documented and independently parameterized.

---

# 6. Longitudinal Learning Dynamics

The student must evolve through time.

Example:

```text
Day 1:
Rotation mastery = 0.31

Day 4:
Rotation mastery = 0.36

Day 10:
Rotation mastery = 0.48

Day 25:
Rotation mastery = 0.42    ← forgetting

Day 30:
Revision intervention
Rotation mastery = 0.57
```

The exact update rules should be selected after literature validation.

Do not assume that a single simplistic linear increase/decrease is psychologically realistic.

---

# 7. Heterogeneous Student Population

Do not generate one generic synthetic student.

Generate multiple learner archetypes and parameter distributions.

Examples:

```text
S01 — strong but careless
S02 — weak but fast learner
S03 — strong concepts, poor time management
S04 — good memory, high forgetting
S05 — strong fundamentals, weak prerequisites
S06 — slow but accurate
S07 — high guessing tendency
S08 — weak concepts + overconfidence
S09 — good on easy questions, poor on hard questions
S10 — highly responsive to guided practice
```

These are hypotheses, not claims about real students. The agent should determine whether they are reasonable synthetic mechanisms and how to parameterize them.

---

# 8. Multiple Synthetic “Worlds”

This is a critical requirement.

The simulator should generate multiple environments with different underlying mechanisms.

Example:

```text
World A → BKT-like learner
World B → strong forgetting
World C → prerequisite-dependent learner
World D → high careless-error behavior
World E → strong time-pressure effects
World F → poorly calibrated confidence
World G → multi-concept interference
World H → different responses to interventions
```

The KT model should not only be tested on the same mechanism used to generate its training data.

Otherwise we risk building a simulator that simply makes the target model look good.

Prefer experiments such as:

```text
Train on Worlds A+B+C
Test on Worlds D+E
```

and similar cross-world evaluations.

# 10. Evaluation Tasks

## A. Latent-State Recovery

Because the simulator knows the true hidden mastery, evaluate whether the KT model estimates it correctly.

Example:

```text
TRUE:
Rotation mastery = 0.34

Observed by model:
Q1 → wrong
Q2 → correct
Q3 → wrong
...

Model estimate:
Rotation mastery = 0.39
```

Measure estimation error/calibration using an evaluation method that is justified by the literature.

Important: establish whether BKT/LKT actually expose a comparable interpretable latent state; do not force a state-recovery metric onto models that are primarily predictive.

## B. Next-Response Prediction

Given interactions up to time `t`, predict:

```text
P(next question correct)
```

Potential metrics:

```text
AUC / ROC-AUC
Log Loss
Brier Score
Calibration
Accuracy (secondary)
```

The agent must justify the chosen metrics from KT literature.

## C. Data Efficiency

Evaluate performance after progressively increasing history:

```text
10 interactions
25
50
100
250
500
1000+
```

This is important for the eventual single-student use case.

## D. Distribution Shift

Train and test synthetic models under different student-generation mechanisms.

This tests whether the learner model generalizes beyond the simulator assumptions.

## E. Intervention Response

Eventually support:

```text
student state
    ↓
intervention
    ↓
student response
    ↓
learning outcome
```

This should be considered a later phase, not required for the first KT benchmark.

# 12. Why BKT Still Matters

BKT is valuable as an interpretable baseline because it explicitly estimates a skill's latent mastery state from sequential responses.

Use it to establish:

```text
“What does an interpretable mastery model tell us?”
```

BKT should not be forced to answer questions about time management, carelessness, intervention effectiveness, or arbitrary behavioral context that are outside its original formulation.

---

# 13. Why PFA / LKT Matter

PFA/LKT are important because the project wants to incorporate multiple observable performance factors.

Potential predictors include:

```text
success count
failure count
recent success/failure
question difficulty
recency
response time
confidence
error-related features
```

The agent must determine which of these are legitimate LKT/PFA features according to the actual literature and which would constitute extensions beyond standard formulations.

The initial goal is to answer:

> **Does a richer feature-based learner model predict future JEE performance better than simpler mastery-only models?**

# 14. Knowledge Graph Layer

Separately from KT, build a lightweight JEE concept graph.

Example:

```text
Vector Decomposition
        ↓ prerequisite
      Torque
        ↓ prerequisite
Rotational Equilibrium
```

Suggested relational representation:

```text

```

A graph database such as Neo4j is **not required initially**.

SQLite can represent these relationships adequately for a first prototype.

The graph should provide context for learner modeling, not replace KT.

# 15. LLM Role

The LLM should not be the numerical student-state calculator.

It can be used for:

- parsing natural-language student input
- extracting concepts
- identifying likely error types
- interpreting written solutions
- extracting confidence/uncertainty signals
- converting messy observations into structured events
- explaining analytical results to the student

Example:

Student:

> “I knew tau = rF, but I used the distance from the center instead of the perpendicular distance.”

LLM output:

```json
{
  "concept": "Torque",
  "error_type": "CONCEPT_APPLICATION",
  "specific_issue": "incorrect lever arm"
}
```

Then the deterministic analytics/KT layer processes the structured evidence.

Principle:

> **LLM interprets; the database and analytics engine calculate and maintain state.**

---

# 16. Important Data-Integrity Principle

Keep three layers separate:

```text
RAW EVIDENCE
    ↓
LLM-DERIVED STRUCTURED EVIDENCE
    ↓
DERIVED STUDENT STATE
```

Never overwrite raw evidence with an LLM interpretation.

For example:

```text
raw_student_text
    ↓
extracted_error_type = CONCEPT_APPLICATION
    ↓
BKT/LKT state update
```

If the extraction model improves later, the structured evidence can be regenerated from the original raw data.

---

# 17. Avoid Data Leakage

Longitudinal interaction data must be split chronologically.

Bad:

```text
randomly split individual attempts
```

Better:

```text
earlier interactions → train
later interactions   → validation/test
```

The agent must specifically audit for:

- future attempts appearing in training
- question metadata derived from future responses
- concept statistics computed using the complete sequence
- student-level leakage between splits
- duplicate/repeated questions appearing across train/test in misleading ways

This is a core requirement for trustworthy KT evaluation.

---

# 18. Do Not Pretend Synthetic = Real

The synthetic dataset should be described as:

> **Synthetic JEE student interaction data generated over real JEE assessment items.**

It is not equivalent to real student data.

Its intended uses are:

```text
controlled experimentation
model development
stress testing
data-efficiency experiments
state-recovery evaluation
benchmarking
```

Future real student data should be used for:

```text
calibration
external validation
transfer evaluation
real-world performance measurement
```

---

# 19. Stronger Validation Strategy

Once real student data becomes available, compare:

```text
A — real-only training
B — synthetic-only training → real test
C — synthetic pretraining → real calibration → real test
```

This allows us to answer the actual research question:

> **Can synthetic JEE learner trajectories reduce the amount of real student data needed to build a useful learner model?**

Do not make this claim until it is empirically measured.

---

# 20. Future StudentSim Direction

StudentSim-style modeling should be treated as a later extension.

The distinction is:

```text
KT:
“What does the student know / how likely are they to succeed?”

Student simulator:
“How will this particular student behave/respond under a given intervention?”
```

A future closed loop could be:

```text
student state
    ↓
candidate interventions
    ↓
student simulator
    ↓
predict response
    ↓
choose intervention
    ↓
real student
    ↓
actual outcome
    ↓
update model
```

Do not implement this in the initial dataset/KT milestone unless validation shows it is immediately justified.

# 23. Final Research Question

The project should ultimately investigate:

> **Can a controlled synthetic population of JEE learners, generated from independently specified learning and behavioral mechanisms, provide a useful environment for training and evaluating lightweight student-performance models such as BKT, PFA, and LKT, and can those models later transfer effectively to real JEE student interaction data?**

The first implementation should optimize for **scientific validity, reproducibility, interpretability, and data integrity** — not model complexity.

# 24. Research Sources and Implementation Leads — VERIFY BEFORE USE

The following sources are starting points, not authorities to copy blindly. The agent must open and verify the original paper/repository, reproduce the relevant claims, and record any assumptions, dataset limitations, and licensing issues before implementation.

## Knowledge Tracing Foundations

1. **Corbett & Anderson (1995) — Knowledge Tracing: Modeling the Acquisition of Procedural Knowledge**
   - DOI: https://doi.org/10.1007/BF01099821
   - Use for: classical BKT formulation, changing student knowledge state, interpretation of initial knowledge, learning, slip, and guess assumptions.

2. **Pavlik, Cen & Koedinger (2009) — Performance Factors Analysis: A New Alternative to Knowledge Tracing**
   - DOI: https://doi.org/10.3233/978-1-60750-028-5-531
   - Full-text/record: https://digitalcommons.memphis.edu/facpubs/8350/
   - Use for: PFA, success/failure history, multi-skill performance, and adaptive-practice motivation.

3. **Pavlik, Eglington & Harrell-Williams (2021) — Logistic Knowledge Tracing: A Constrained Framework for Learner Modeling**
   - DOI: https://doi.org/10.1109/TLT.2021.3128569
   - Repository/full-text record: https://digitalcommons.memphis.edu/facpubs/8158/
   - Use for: LKT framework, logistic learner models, feature specification, model comparison, student-level differences, and recent-learning features.

4. **Piech et al. (2015) — Deep Knowledge Tracing**
   - arXiv: https://arxiv.org/abs/1506.05908
   - Use for: understanding the transition from explicit mastery models to learned sequential representations; do not assume the reported gains transfer automatically to JEE.

5. **Nakagawa, Iwasawa & Matsuo (2019) — Graph-based Knowledge Tracing: Modeling Student Proficiency Using Graph Neural Network**
   - DOI: https://doi.org/10.1145/3350546.3352513
   - Use for: graph-structured knowledge components and relational inductive bias in KT.

6. **ReKT — Revisiting Knowledge Tracing: A Simple and Powerful Model**
   - Official implementation referenced by pyKT: https://github.com/lilstrawberry/ReKT
   - Use for: modern KT architecture comparison; verify paper metadata, task setup, datasets, and whether pretrained checkpoints exist before considering transfer to JEE.

## Synthetic Student / Simulation Research

7. **Pagonis et al. (2024) — Analysis of Knowledge Tracing performance on synthesised student data**
   - arXiv: https://arxiv.org/abs/2401.16832
   - Use for: direct precedent for synthetic student interaction data, synthetic-vs-real KT experiments, and limitations of synthetic augmentation.
   - Important claim to verify directly: their abstract reports that training with only synthetic data achieved similar performance to real data in their experiments, while adding synthetic data to real data produced only minor additional improvement.

8. **StudentSim (2026) — Training LLM-based Student Simulators**
   - arXiv: https://arxiv.org/abs/2609.01591
   - Code: https://github.com/microsoft/StudentSim
   - Use for: individualized student simulation, sparse per-student data, behavioral fidelity, guidance responsiveness, and later intervention-simulation work.
   - Do not treat StudentSim as a KT replacement; it addresses a related but different problem: predicting how an individual learner responds to tutoring/guidance.

9. **L-HAKT (2026) — verify exact paper title, authors, and released implementation before citing**
   - AAAI proceedings: https://ojs.aaai.org/index.php/AAAI/article/view/38494
   - Use for: LLM-assisted hierarchical knowledge construction, student-agent simulation, synthetic learning behavior, and synthetic/real alignment.
   - Agent must read the full paper and verify every reported result before relying on it.

## Research Methodology Requirements

16. **Primary-source-first rule**
    - Prefer original papers, official repositories, official dataset cards, and original benchmark pages.
    - Search snippets, blog posts, and secondary summaries are discovery tools only.

17. **Reproduce before believing**
    - For every important paper, record:
      - dataset(s)
      - number of students
      - number of interactions
      - feature schema
      - train/validation/test protocol
      - leakage controls
      - metrics
      - baseline models
      - reported results
      - limitations
      - availability of code/checkpoints

18. **Synthetic-data validity rule**
    - Never claim synthetic JEE interaction data is equivalent to real student data.
    - Use synthetic data first for controlled development, stress testing, state recovery, model comparison, and data-efficiency studies.
    - Validate transfer to real students separately when real data becomes available.

19. **Model-independence rule for simulation**
    - The synthetic student generator must not simply be the same mathematical mechanism as the KT model being tested.
    - Otherwise the benchmark becomes circular and artificially favors the target model.

20. **Longitudinal evaluation rule**
    - Predict future responses from past interactions.
    - Avoid random row-level splits that allow temporal leakage.
    - Consider student-level and time-based holdouts where appropriate.

21. **Baseline-first rule**
    - Always compare sophisticated KT models against simple baselines.
    - At minimum:
      - recent accuracy
      - PFA
      - BKT
      - LKT
    - Later models such as ReKT/GKT/DKT should only be introduced when the data size and research question justify them.
